# ForeBalance UX review · November 9, 2026

ForeBalance already makes the current scenario easy to scan. The next improvement is to make the consequences of a decision equally easy to read. Someone comparing two plans should be able to see which payment changed, what it does to checking, and which scenario will receive it.

## 1. Make Compare and Merge tell the same story

**Fix Compare first.** Source inspection shows that Compare pairs raw lines by position. Insert one bill above three existing bills and the unchanged bills can appear edited. Its debt table also iterates only the left scenario’s accounts. A credit card added to the right scenario can be missing from the comparison. These affect what a person sees immediately before making a merge decision.

Align common entries across insertions, compare debt accounts from both scenarios by ID, and distinguish an absent account from a paid-off account. Keep the distinction between comparing two current scenarios and identifying changes since a fork. The former can compare any pair. The latter has a common starting copy only for newer forks. The comparison and merge screens can share entry descriptions and field formatting while retaining those different rules.

**Make the choice readable.** In the rendered conflict, the heading was “Update · Rent” and the user had to compare two PSV strings to discover that the original had $110 and the fork had $125. Show **Rent · Monthly payment** followed by **$110 → $125**. Name the destination in the apply button or directly above it. Put exact PSV under “View entry text.” Keep raw details visible for changes that cannot be summarized faithfully, including comments, unknown fields, and blocks of multiple lines. Distinguish additions, removals, payment changes, and dated debt resets.

Keep explicit selection and the existing history recovery. Render an unselected Apply button with a clearly inactive treatment. On a narrow screen, stack labeled values and keep the selection count and action reachable while the list scrolls. For conflicts, include the starting value when available so someone can see how both versions diverged. Older forks need the existing manual-review explanation.

**Acceptance example.** Insert a new card before Rent in a fork. Compare shows the added card and its debt, and Rent stays out of the change list. Change Rent independently in both scenarios. The merge preview identifies both amounts and the destination before anything is applied.

Primary files are `src/lib/forecast/scenarioCompare.ts`, `src/components/ScenarioCompare.svelte`, `src/lib/data/scenarioMerge.ts`, and `src/components/ScenarioMerge.svelte`.

## 2. Make the forecast controls match the unit of change

The month list scrolls independently and the goal and lowest-balance links already jump to the relevant rows. Preserve those interactions. The sample summary showed “Goal reached $3,535” beside “Goal $2,500.” Give each number a role, for example “First above $2,500 · Nov 29” with “Balance $3,535” at the destination. Give the lowest point and next threshold crossing priority over the persistent instructions and legend.

The checkbox sits on a dated occurrence, yet turning it off disables its entire source entry. Someone looking at November rent could reasonably expect to skip only November. Expose “Edit this occurrence” on the row and put “Disable recurring entry” in its actions. For a one-time entry, use “Disable entry.” If the app offers a recovery action, tie it to re-enabling that exact source. Keep the existing same-day and occurrence overrides accessible.

**Acceptance example.** Someone viewing November rent can identify whether an action affects November or every rent payment before choosing it. Retain keyboard access to both actions.

Primary files are `src/components/ForecastTable.svelte`, `src/components/ForecastSummary.svelte`, and `src/components/ForecastSparkline.svelte`.

## 3. Use the starter to teach categories and bulk updates

The rendered Close month starter showed 14 tiles and 13 unfiled entries. Rent, groceries, and a credit card had the same folder icon. The layout already has room for category icons and a category filter. Assign categories to newly created starter entries so someone can discover those features by looking at a recognizable bill. Keep saved scenarios and user category assignments intact. Use the same term, “Category,” in the Entries filter, its menu, and the bulk panel.

For the monthly card update, keep one compact row per account. Honor the selected category. When opened from All, prefer Credit cards if it has editable card balances, then fall back to another eligible group. The current code prefers Debt payments when present. Replace the generic toolbar label “Bulk update” with “Balances & payments” if it fits, and keep the effective date visible beside the balance heading. Explain the category lock only when it occurs, for example “Save or cancel these edits to switch category.”

**Acceptance example.** In a fresh sample, the card icon, Credit cards filter, and bulk panel lead to the same entry. A payment-only change leaves the dated balance alone.

Primary files are `src/lib/data/entryTemplates.ts`, `src/components/EntryCards.svelte`, and `src/components/BulkPayments.svelte`.

## 4. Let Labs start with a question someone can answer today

Labs initially displayed compatibility, model choices, and a load button. “What hits next?” already answers from local forecast data. Open Labs on Explore forecast with that action available whenever the scenario has a forecast. Place model setup beside the questions that require it. If someone chooses Draft entries and loads a model, return them to their draft. The current success path always switches to Explore forecast.

Keep the active scenario visible beside each result. If there is no forecast, link to Entries. If model loading fails, keep the question and offer retry. Put routing details behind the existing disclosure and announce the answer where the user initiated the action.

**Acceptance example.** In a clean session, one click after opening Labs produces upcoming transactions. Starting model setup from Draft entries returns to the same task after loading.

Primary file is `src/components/Labs.svelte`.

## 5. Keep the quieter surfaces and improve their first choice

Welcome’s dark opening panel, current scenario summary, and collapsed examples give it a clear hierarchy. For a returning user with an active scenario, lead with that scenario’s forecast and keep “Edit entries” beside it. Keep the current example-led introduction for a first visit. Base this decision on a known saved user scenario or an explicit preference, since default starters also exist on first load.

Settings, Help, and Labs share a section rail that becomes a labeled selector on narrow screens. Keep it. Help’s “Getting started” currently opens with PSV grammar, while Entries opens in Visual. Lead with a short route through adding a paycheck and a bill and reading the lowest balance. Keep TYPE, WHEN, and the raw reference directly reachable. In Settings, break the display-currency paragraph at the decision that matters most: amounts retain their numeric values and changing currency rescales the threshold marks. Put import and export behavior with saving guidance.

## Evidence and delivery order

The review used the local build at commit `f1a374c`, disposable browser storage, and synthetic data. All six tabs were rendered at 1280 × 760. A conflicting rent change was opened at desktop width and inspected at 390 × 720. Compare’s alignment and debt coverage, bulk defaults, disabling behavior, and Labs return navigation were traced in source. This was a design review without participant or physical-device testing.

Deliver Compare accuracy and readable merge decisions first. Follow with forecast action scope, starter categories and bulk editing, then Labs entry and return behavior. Welcome, Settings, and Help refinements can follow independently. Each acceptance example is a focused check for its proposed change.
